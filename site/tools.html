Tools

rigid's compiler keeps an exact reference graph as a byproduct of resolution — not reconstructed afterwards, not approximated. These are the questions that becomes decidable once it does. Every transcript below is real output, not an illustration.

Why these exist

A definition's identity is the hash of its canonical form, with bound names erased and every reference replaced by the hash of what it points at. Two consequences drive everything on this page. A rename moves no hash, so the tools can tell a rename from a rewrite. And a hash covers the whole dependency cone, so a claim about one definition is a claim about everything it reaches.

Elsewhere these questions are answered by heuristics: a structural differ guesses at renames, an import linter approximates the call graph, a review approval is bound to a diff. Here they are answered by the same resolution the compiler already performed.

diff — grade a text diff by identity

Two revisions are compared as sets of identities. The report separates two questions, because they have different victims: whether any definition changed meaning, and whether any name moved. Below, the definition was renamed, every parameter was renamed, and the body was reflowed onto seven lines. Not one line of util.rg survived.

$ rigid diff --against ../before
3 definitions before, 3 after — 2 identical

  renamed   util.rg#clamp  ->  util.rg#clip

meaning   unchanged — provably semantics-preserving
          every identity on both sides is the same set, so no
          definition can behave differently.
surface   1 name(s) moved — behaviour is intact, but callers
          outside this workspace refer to them by name

Equal hash sets on both sides prove no definition can behave differently, whatever the text shows. A rename still breaks callers outside the workspace, which is why surface is reported separately rather than folded into a single verdict.

--require-no-semantic-change exits non-zero when meaning moved, so a pull request that claims to be a pure refactor can be made to prove it. --save records a baseline for a later bare rigid diff.

merge — a rename and an edit are different coordinates

Definitions are paired across three revisions by identity first and name second: a surviving hash is the same definition whatever it is called, and a surviving name is the same definition whatever it now does. Name and body then resolve independently.

# ours renamed clamp to clip. theirs changed what it does. Same lines.
$ rigid merge --base base --ours ours --theirs theirs -o merged
  take Theirs   app.rg#main
  merged     u.rg#clip  (ours renamed it, theirs changed what it does — kept both)

2 definitions considered, 0 conflicts.
1 merged on both coordinates at once — a rename on one side and an
edit on the other. A line-based merge reports those as conflicts,
because it cannot see that the two changes are about different things.


$ cat merged/u.rg
// clamp into a range
fn clip(x, lo, hi) {
  return if (x < lo) lo else if (x >= hi) hi - 1 else x;
}
$ rigid check --root merged && rigid run app.rg#main 20
ok: 2 module(s), 2 definition(s), 2 hashed
9

Git reports that as a conflict — the same lines changed on both sides — because it cannot see that one side moved a name and the other moved a meaning. Two sides that rename differently still conflict, and so do two that edit differently; nothing is written until they are resolved.

attest and trust — evidence bound to identity

A claim about a definition — reviewed, audited, benchmarked, generated — binds to that definition's hash rather than to a commit or a diff. It is live while the hash is current and void the moment it is not.

$ rigid attest api.rg#handler --kind reviewed --by david
attested reviewed api.rg#handler
  identity sha256:1081d87ac59fc8e4c0fba700a07dd0a30d8220f9a9a9405bebfb85628fcbb3b6
  covering 3 definition(s) in its cone — an edit to any of them
  moves this hash and voids the claim.

# someone edits sanitize — two modules and three calls away
$ rigid trust api.rg#handler
api.rg#handler  sha256:efc0aa8a1b51134a3bf92f8afea6af75e63cf43ca20116dcad9e63eac3180bf2

no live claim about this definition.

stale — made about a version that no longer exists:
  reviewed   by david on 2026-08-05

Because a hash covers its cone, reviewing handler attests to everything handler reaches. The edit above was three calls away in another module and the review went void without anyone deciding it should. A rename anywhere in that cone would not have, because a rename moves no hash.

Every other review system binds approval to a diff, so it survives a rebase that changed the logic and dies on a rename that changed nothing. Stale claims are kept rather than deleted: unreviewed and stale are different facts. rigid check --require reviewed fails the build unless every definition carries a live claim of that kind.

caps — what reaches the outside world

Effects are a declared set — !io !fs !net !env !time !rand !proc — and every capability enters through an extern. Propagation follows the exact graph, so the listing is complete by construction rather than by search.

$ rigid caps
5 definitions, 1 pure.

!net    2 definition(s)
        via extern host.rg#fetch = "globalThis.fetch"
          app.rg#download
          host.rg#fetch

!time   2 definition(s)
        via extern host.rg#now = "Date.now"
          app.rg#stamp
          host.rg#now

Every capability enters through an extern and travels the exact
graph, so this list is complete by construction, not by search.

Capabilities are part of canonical form, so they are part of identity: an imported definition that gains one gets a new hash, and its importer's sidecar reports the widening by name as W0405 — an error under --frozen. Measured across 3,533 consecutive npm upgrades, a patch release widens its capability set 0.5% of the time, which is what makes that check worth leaving on. See the evidence.

dead — what nothing can reach

Roots are every test_* definition, anything named main, and any --entry given explicitly. The answer is a proof rather than a guess.

$ rigid dead
9 of 16 definition(s) unreachable from any test, any `main`.

1 nothing in this workspace references at all:
  pipeline.rg#triage

8 reachable only from those:
  pipeline.rg#log
  pipeline.rg#notify_oncall
  pipeline.rg#queue_normal
  pipeline.rg#escalate
  pipeline.rg#route_network
  pipeline.rg#route_database
  pipeline.rg#route_access
  pipeline.rg#routes

This is the compiler's own resolution, not a search: nothing here can
reach them. Each name in the first list is a decision — an entry point
to declare with --entry, or code to delete. The second list follows.

The split matters. Definitions nothing references at all are decisions — an entry point to declare, or code to delete. Everything beneath them follows automatically, so a list of nine becomes one thing to think about.

why, deps, rdeps — the graph itself

rigid deps and rigid rdeps list outgoing and incoming references. rigid why answers the question behind them: if this changes, what gets a new hash, which tests re-execute, and by what path.

$ rigid why score.rg#severity
score.rg#severity  sha256:27f823254df68f2937d0872713b658cb54a8163fa6d94b10e41f4f64d5e5776c

if this changes, 7 definition(s) get a new hash:
  pipeline.rg#route_network
  pipeline.rg#route_database
  pipeline.rg#route_access
  pipeline.rg#triage
  pipeline.rg#routes
  tests.rg#test_severity_clamps
  tests.rg#test_severity_floor

and 2 test(s) re-execute, because:
  test_severity_clamps -> severity
  test_severity_floor -> severity

The path is the reason, not a guess at one — it is the chain of references the compiler resolved. That is also what makes the test cache sound: an unchanged hash is a provably identical rerun, so rigid test skips it rather than hoping.
